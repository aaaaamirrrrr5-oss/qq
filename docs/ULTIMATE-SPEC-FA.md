# سند رسمی الزامات و معماری Site Manager 3.12.0 Ultimate

وضعیت: سند الزام‌آور توسعه؛ نسخه محصول نهایی محسوب نمی‌شود.

## اصول غیرقابل مذاکره
1. هر قابلیت فقط پس از تکمیل UI، منطق، API، Backend، مجوز سمت سرور، ذخیره واقعی، مدیریت خطا و تست معتبر «کامل» اعلام می‌شود.
2. داده ساختگی، دکمه بی‌عملکرد و پاسخ Mock در مسیر عملیاتی ممنوع است.
3. فایل‌ها و کد قالب‌های شخص ثالث مطلقاً تغییر نمی‌کنند. هیچ فایلی در پوشه قالب ایجاد یا ویرایش نمی‌شود.
4. در صورت نبود API رسمی یا Adapter امن، قابلیت فقط‌خواندنی یا «نیازمند اتصال اختصاصی» اعلام می‌شود.
5. تمام گزارش‌ها، مستندات، پیام خطاهای قابل مشاهده و پرسش‌ها فارسی هستند؛ رابط باید RTL فارسی/عربی و LTR انگلیسی را پشتیبانی کند.
6. تحویل نهایی تنها پس از تحویل Android source، افزونه ZIP نصب‌شدنی، APK نصب‌شده/آزمایش‌شده، مستندات و گزارش تست واقعی مجاز است.

## معماری مشترک
- Android UI
- Application/service layer
- Versioned REST API
- WordPress Bridge
- Authentication و capability validation
- Policy engine و tenant isolation
- WordPress/WooCommerce/framework APIs
- Database
- Audit log و پاسخ قابل ردیابی
- Integration و device tests

تمام قابلیت‌های حساس باید از همان موتور احراز هویت، مجوز، ثبت رویداد و پاسخ خطای استاندارد استفاده کنند.

## مدیریت قالب
- شناسایی پوسته فعال، نام، نسخه، پوسته والد/فرزند و قابلیت‌های مرتبط.
- Schema پویا با شناسه پایدار، نسخه، اثر انگشت، گروه، توضیح، آیکون، نوع کنترل، قابلیت، مقدار پیش‌فرض، محدودیت و Adapter.
- Adapter مستقل برای Customizer، Settings API، Redux، Kirki، ACF Options و تنظیمات اختصاصی.
- Adapter فقط در صورت کشف API/ساختار واقعی ثبت می‌شود؛ کشف فریم‌ورک به‌تنهایی مجوز نوشتن نیست.
- نوشتن فقط از API رسمی مالک تنظیمات، با capability، nonce/REST auth، sanitize و validate سمت سرور.
- پشتیبانی کنترل‌ها: text, number, color, media, icon, font, toggle, select, multiselect, range, rich text, URL, dimensions, repeater, group و conditional.
- تغییر Schema باید قابل تشخیص باشد؛ گزینه‌های قدیمی بدون migration امن حذف یا جابه‌جا نمی‌شوند.
- پشتیبان‌گیری/بازگردانی برای عملیات حساس و گزارش خطای قابل فهم الزامی است.
- Beano Coffee فقط نمونه آزمایشی است؛ فایل‌های قالب در تمام مراحل read-only باقی می‌مانند.

## مدیریت هوشمند کارکنان
- مجوزها به صورت deny-by-default و چندبعدی: عملیات، داده، فروشگاه، شعبه، انبار، سفارش، مشتری، محصول، دسته، مبلغ، زمان، دستگاه و IP.
- فیلتر داده قبل از ساخت JSON اعمال می‌شود؛ اطلاعات غیرمجاز نباید در پاسخ وجود داشته باشد.
- دسترسی واقعی بر پایه capability وردپرس به‌علاوه policy اختصاصی محدودکننده است؛ policy هرگز capability جدید اعطا نمی‌کند.
- گردش تأیید برای بازپرداخت، حذف، قیمت، موجودی عمده، نقش/مجوز، تنظیمات امنیتی و صادرات مشتری.
- Audit log تغییرناپذیر تا حد امکان: actor، tenant، action، target، قبل/بعد امن‌شده، زمان، نتیجه و approval chain.
- گزارش عملکرد فقط از رخدادهای واقعی و قابل ردیابی محاسبه می‌شود؛ معیار و بازه زمانی باید نمایش داده شود.

## مرکز کنترل چندفروشگاهی
- فهرست اتصال‌ها، نام، گروه، وضعیت، نسخه‌ها، سلامت API و آخرین همگام‌سازی.
- کلید/اعتبارنامه مجزا برای هر فروشگاه؛ رمزها در خروجی عادی API یا لاگ ثبت نمی‌شوند.
- هر درخواست شامل tenant/site identity معتبر است و Bridge سمت سرور مالکیت و دسترسی را اعتبارسنجی می‌کند.
- داده‌ها بین فروشگاه‌ها جدا می‌مانند؛ خطای یک فروشگاه نباید باعث تکرار یا پنهان شدن خطای دیگر شود.
- داشبورد تجمیعی باید از داده واقعی با ارز، منطقه زمانی و وضعیت همگام‌سازی روشن ساخته شود.
- عملیات گروهی: ابتدا dry-run/preview، سپس تأیید، سپس اجرای مستقل و گزارش نتیجه هر فروشگاه.

## دستیار هوشمند عملیاتی
- ابزارهای AI از allowlist قابلیت‌های Backend استفاده می‌کنند؛ مدل مستقیماً SQL یا option دلخواه اجرا نمی‌کند.
- ابزارها با هویت و مجوز کاربر فراخوانی می‌شوند؛ prompt injection از محتوا/نظر/محصول نباید اختیار ایجاد کند.
- تحلیل‌ها فقط از داده واقعی و مجاز و با بازه/منبع روشن تولید می‌شوند.
- عملیات تغییردهنده ابتدا preview شامل target، مقدار فعلی، مقدار پیشنهادی و اثر را ارائه می‌کند.
- عملیات حساس نیازمند تأیید صریح مجدد و سپس اجرای Backend است.
- درخواست، پاسخ مدل، ابزار، تأیید، نتیجه و خطا در Audit ثبت می‌شود؛ کلیدها و داده حساس redact می‌شوند.
- سقف هزینه، محدودیت نرخ، خاموش‌کردن قابلیت و سیاست نگهداری داده الزامی است.
- ارائه‌دهنده AI و هزینه‌ها باید پیش از فعال‌سازی عملیاتی تعیین شوند.

## کیفیت محصول
- نقش‌محور بودن منو و داشبورد، جست‌وجوی سراسری، میانبرها، فیلترهای ذخیره‌شده، اعلان‌ها، وضعیت همگام‌سازی، حالت روشن/تاریک، تبلت و دسترس‌پذیری.
- RTL فارسی/عربی و LTR انگلیسی در تمام صفحات و کنترل‌ها.
- عدم استفاده از Mock در build انتشار.

## معیارهای پذیرش و گزارش
برای هر قابلیت: مسیر UI، endpoint، callback، capability، policy، ذخیره واقعی، اثر در سایت، audit، خطاها، تست مثبت/منفی و سازگاری نسخه ثبت می‌شود.
گزارش هر مرحله شامل هدف، بررسی، تغییرات، فایل‌ها، API، تست، نتیجه، مشکلات، وابستگی و نقطه ادامه است.
تست staging و APK روی دستگاه واقعی برای ادعای عملکرد عملیاتی الزامی است.

## وضعیت جاری
در نسخه توسعه‌ای dev1:
- API یکپارچه read-only برای Schema پوسته و وضعیت Adapterها اضافه شده است.
- گزینه‌های WordPress Settings API که صریحاً show_in_rest شده‌اند در اپ قابل نمایش و ذخیره از مسیر `/registered-settings` موجود هستند.
- Beano adapter موجود حفظ شده است.
- Customizer/Redux/Kirki هنوز نیازمند Adapter نوشتن اختصاصی‌اند؛ ACF در این نسخه فقط شناسایی می‌شود.
- کارکنان چندبعدی، گردش تأیید، تجمیع چندفروشگاهی و دستیار عملیاتی هنوز تکمیل و تست زنده نشده‌اند.
